# Apply reviewed changes

1. Start only from a reviewed artifact that lists tenant, subscription, full resource IDs, referenced content, parameters, each operation, and expected effects, and from explicit user approval of that exact set. If any part of that exact approval is missing, stop and wait. Brief acceptance, broad "build and apply", another model's review, or approval of a different operation set is not consent.
2. Use only already available authenticated interfaces. No auto-install, login repair, retries, rollback, delete, or cleanup. Grants, deletes, annotations, discovery writes, explicit external reports, and unrelated resource effects are separate writes that each need explicit user approval and are never implied by model update approval. Use [operation checks](references/operations.md) for execution syntax and validation boundaries.
3. Immediately before each write, recheck caller identity, tenant/subscription, explicit per-call scope, current target preconditions, and approved artifact identity. Pass approved tenant, subscription, and full resource IDs explicitly on each call, and reject any scope mismatch. Denied, partial, or uncertain precondition reads block the write. Any change in artifact, params, scope, effects, or drift requires renewed explicit approval.
4. Execute only the approved subset. If approval is partial, run only that subset. If approval is withdrawn or changed after writes begin, stop further writes and report completed operations. Do not run unapproved diagnostic or probing writes. On any operation failure or uncertain response, stop further writes and reconcile read-only.
5. After writes, read back affected native configuration and compare against the reviewed expected state for the same scope, including intended entities, relations, signals/groups, bindings, and preserved unrelated writable fields. If mismatched, stop further operations, report diffs by resource ID, and wait. Do not autocorrect. If operation completion or evaluated status is pending, report unknown until confirmed by attributable readback evidence.
6. Report actual outcomes as success, failure, unknown, or partial, plus source timestamps/windows and remaining verification gaps. Report denied, throttled, truncated, or partial reads and writes explicitly as unverified coverage where applicable. Provisioning or request success alone is never proof of configuration match or evaluated health. Keep approval and readback evidence needed for verification in a short clause with source, scope, caller identity, and time.
